# PR title

feat(libllama): load-time assembly of per-layer GGUF parts

# PR body

## Summary

Adds single-layer model file support: a GGUF "layer library" of one-block
files (`blk-NNNNN.gguf` + `parts-*.gguf`) that is assembled into a working
model at load time, for any absolute layer window `[A,B)`. Re-balancing a
stage pipeline no longer requires re-slicing multi-GB monolithic files and
redistributing them — any window is assembled from the same library on the
spot.

- `examples/stage-runner/slice_gguf_layers.py` — one-time slicer that writes
  the per-layer library plus a `manifest.json`
  (`gguf-layer-library/v1`, blake2b-128 provenance hashes). Ops-only: the
  loader discovers files by name and reads shape KVs from the GGUF headers.
- `llama_model_load_from_parts(const struct llama_model_part *, size_t,
  struct llama_model_params)` — new libllama entry point
  (`struct llama_model_part { const char * path; int32_t blk_base; }`).
  Each part file's `blk.J` tensors are remapped to `blk.(blk_base+J)`;
  `{arch}.block_count`, `leading_dense_block_count` and
  `nextn_predict_layers` are re-derived as the sum of per-file values and
  injected as internal KV overrides (explicit user `--override-kv` still
  wins). Gaps or out-of-window block indices abort the load with a clear
  error.
- Backend-agnostic and mmap-first (one mmap/file handle per part, no double
  copy); the monolithic `-m` path is untouched.
- `examples/stage-runner/LAYER_SLICES.md` — library format, manifest schema,
  launch-parameter design and verification log.

Stage-binary wiring (`--model-dir DIR --layers A,B --stage-parts SPEC` on
`llama-stage-runner`) is a planned follow-up on top of this API; the design
is recorded in `LAYER_SLICES.md` §3 and the flag surface is intentionally
not in this PR.

## Verification

CUDA build (nvidia, 6× RTX 5060 Ti, CUDA 13.0, sm_120):

```
$ cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=120 -DLLAMA_CURL=OFF
$ cmake --build build --target llama-stage-runner -j16
[100%] Built target llama-stage-runner
```

Slicer regenerates the library from the monolithic TinyLlama-1.1B Q4_K_M:

```
$ PYTHONPATH=gguf-py python3 examples/stage-runner/slice_gguf_layers.py \
    tinyllama-1.1b-q4_k_m.gguf lib
[lib] DONE 24 files, 0.67 GB tensor data -> lib
```

Loader-level assembly (harness calling `llama_model_load_from_parts` with
explicit `path:blk_base` parts), window [0,5) = embd + blk 0..4 + output:

```
llama_model_loader: assembled 7 parts: block_count=5 leading_dense_block_count=0
  nextn_predict_layers=0 (48 tensors)
validate_override: Using metadata override (  int) 'llama.block_count' = 5
llm_load_print_meta: n_layer          = 5
llm_load_print_meta: n_embd           = 2048
n_layer=5 n_embd=2048
OK
```

Full window [0,22) = 24 parts vs the monolithic file — in-memory tensor
hashes (`LLAMA_DUMP_TENSOR_HASH=1`, 201 tensors):

```
tensor hashes: assembly 201 | mono 201
ALL TENSOR HASHES IDENTICAL (24-part assembly == monolithic)
```

Gap in the window (blk 0,1,3) aborts with a clear error:

```
llama_model_load: error loading model: invalid assembly: no tensors for blk.2
  (window block_count=3)
```

## Notes

Part of the ik_llama.cpp fork preparation. Equivalence to monolithic slices
was previously established on CPU (2026-07-12, see `LAYER_SLICES.md`):
per-window tensor-hash equality, temp-0 generation parity, and byte-identical
hidden-state emit.
